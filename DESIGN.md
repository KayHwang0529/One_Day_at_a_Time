At the root of the repository project.godot defines the overall Godot project settings and autoloads; main.gd contains the startup logic and instantiates the initial scene to kick off the game. As the game title suggests, I wanted to portray a day in the life from beginning to end, hence why I chose the "home" setting to be the intial scene. Complementing these, the data.pandora file and the pandora/ folder provide the infrastructure for the inventory that allows users to pick up items for the sake of progressing through quests. Alongside documentation files (such as README and DESIGN), the layout then branches into several well-defined subfolders that delineate responsibilities. The scenes/ folder contains the various .tscn files that define game screens, environments, UI panels, and in-game entities such as player, NPCs, and world objects. Separately, scripts/ hosts the behavior and logic: movement, player control, camera, UI logic, game state management, quest orchestration, inventory and status tracking, scene transitions, and more. For quest logic specifically, a subfolder scripts/queststeps/ contains concrete quest-step implementations derived from abstract base classes. Static game content like quest definitions and dialogue data are kept in resource files under folders like quests/ and dialogue/. All graphical, audio, and UI assets are stored under an asset folder (noting that it is currently named assests/), consolidating sprites, tilesets, fonts, sounds, and UI graphics. Finally, the project includes custom plugins and tooling under the addons/ folder — namely modules handling dialogue management, data entity editing/persistence, and quest system support.

This organization reflects a deliberate commitment to separating concerns: visual layouts and content (scenes and resources) remain distinct from behavior (scripts) and from tooling (plugins). Such segregation promotes reuse, and makes the codebase easier to, maintain, and extend. By storing data in resources (for quests, dialogue, inventory templates, etc.), the system enables content creators to author or tweak game content without touching logic, while the core systems (quest execution, inventory semantics, UI binding) remain insulated and stable.

Within the script architecture, core systems like global game state management, scene loading and transitions, player control and camera behavior, inventory and item handling, quest orchestration, dialogue parsing, UI logic, and status tracking are cleanly separated. For example, a base quest class defines the contract and lifecycle for quests, while each concrete quest step is implemented in its own script file. Inventory logic remains separate from UI representation, and UI scenes simply bind to domain state rather than handling logic themselves. This architecture uses scene/component composition, base-class inheritance for abstractions, plugin/adapter patterns for extensibility, and resource-driven data to preserve flexibility. This allowed me to add my pixel art into the UI of the game, whilst adding code to create alterations based on game status and progression. The resulting structure supports feature expansion without entangling subsystems, making it suitable for iterative development.

Beyond code and systems, the project treats visual style — especially color usage — as a central, intentional component of design rather than an afterthought. The art and UI are built according to a curated, limited palette that unifies the game’s aesthetic across scenes, environments, UI screens, and interactable elements. By restricting the range of hues and carefully assigning color roles — background environment, ambient details, interactive objects, UI elements, highlights — the game maintains visual cohesion and avoids what might otherwise become a chaotic or disjointed look. It also allows for a clear distinction between normal mode and "anxiety" mode that appears when stress level exceeds a certain threshold. For context, this "anxiety" mode entails an increase in saturation and a shift in hue.

Color is also used as a functional tool to convey meaning and guide player attention. Interactive or important objects — items the player can collect, quest-relevant props, pickups — are marked with accent or highlight colors so that they stand out against the environment. For example, the red headphones and main character's shirt are able to stand out against the largely cool-toned school environment.

Moreover, the design allows for mood and narrative signaling through color. Scenes meant to evoke calm, safety, or normal everyday life might use softer, muted palettes. Conversely, tense or dramatic narrative moments might shift toward higher contrast, different lighting or color temperature, or more saturated accents — using visual tone to reinforce storytelling and emotional atmosphere. Because all assets, artifacts, UI skins, environment tiles, sprites, and UI elements are managed centrally (via resources and scenes), these style shifts can be applied broadly and consistently. This makes the palette not just a static choice but a dynamic tool linked to narrative and gameplay context.
